This file explains how people can contribute to the project. This file can help verify people are submitting well-formed pull requests and opening useful issues.

## Reporting bugs

- Search existing issues before opening a new one.
- Use the issue template in `.github/ISSUE_TEMPLATE/MAIN.MD`.
- Include clear reproduction steps, what you expected to happen, what actually happened, and your environment (browser, OS, and so on).
- Include screenshots or logs when they help explain the problem.
- Report one bug per issue.

## Feature requests

- Open an issue to discuss a feature before writing code for it.
- Explain the problem the feature solves and who it helps.
- For large or breaking changes, wait for agreement on the approach before opening a pull request.
- Unsolicited large pull requests may be declined or asked to start as an issue.

## File naming and layout

- Markdown files use an uppercase `.MD` extension (for example `README.MD`, `docs/CODEOWNERS.MD`). Do not introduce `.md` files.
- Repository policy files live at the root (`CONTRIBUTING.MD`, `LICENSE.MD`, `README.MD`).
- GitHub configuration lives in `.github/` (issue and pull request templates, workflows).
- Site pages live in `docs/`; ownership rules are documented in `docs/CODEOWNERS.MD`.
- More file and folder conventions will be documented here as the project grows.

## Generated files

- Every `docs/*.html` page and `docs/index.html` is generated by `scripts/build-index.mjs` from the `.MD` files in `docs/`.
- Never edit generated HTML by hand. Edit the `.MD` source instead.
- After changing anything in `docs/`, run `node scripts/build-index.mjs` and commit the regenerated files along with the source change.
- Markdown outside `docs/` is not part of the generated site.

## Commit style

Use [Conventional Commits](https://www.conventionalcommits.org/):

```text
<type>(<scope>): <summary>
```

- Types: `feat`, `fix`, `docs`, `style`, `refactor`, `test`, `chore`.
- Write the summary in the imperative mood, lowercase, with no trailing period (for example `docs(contributing): add pull request limits`).
- Keep each commit focused on one change. Split unrelated work into separate commits.
- Reference issues in the body or footer when relevant (for example `Closes #12`).

## One logical change per PR

- Each pull request should contain one logical change: a single fix, feature, or documentation update.
- Do not bundle unrelated refactors, formatting changes, or fixes with a feature.
- Split large work into smaller, reviewable pull requests.
- Unrelated changes may be asked to move to a separate PR before review.

## Contributor License Agreement

Before a pull request can be merged, you must agree to the Contributor License
Agreement in `CLA.MD`. This is handled automatically:

- The **CLA Assistant** GitHub App checks every pull request.
- If you have not signed, the app posts a comment with instructions.
- Signing is a one-time action per contributor.

The CLA grants the Project Owners a perpetual, irrevocable, royalty-free license
to your contribution, including the right to relicense it under commercial terms.
See `CLA.MD` for the full text.

## Pull request limits

This repository has temporary interaction restrictions enabled.

- Each user may have at most **2 open pull requests** at a time.
- **Draft pull requests count toward the limit.**
- If you are at the limit, close or merge an existing pull request before opening another.
- These limits are temporary and may change or be lifted at any time.

### Enforcement

- Pull requests opened beyond the limit may be closed without review.
- Reopening or re-creating a closed pull request to bypass the limit may result in further interaction restrictions.
- Mark a pull request as ready for review only when it is complete, since drafts count toward the limit.

## Review process

- Code owners are defined in `docs/CODEOWNERS.MD` and are automatically requested for review on matching changes.
- Required approvals and passing checks must be satisfied before a pull request is merged.
- Respond to review feedback or explain why a suggestion does not apply.
- Keep discussions on the pull request focused on the change.
